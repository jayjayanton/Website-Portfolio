The problem

What needed to be understood or built?

A distinctive sports identity needs a coherent website across fighter profiles, events, media and merchandise. The interface must preserve its visual character while remaining usable on smaller screens and across English and Spanish content.

My contribution

The work I was responsible for.

I maintain a public fork of the Ra’az Borg frontend as part of ongoing website development. The repository establishes the current interface and its features, but the available record does not yet isolate every change I made. This case study therefore preserves upstream attribution and does not claim sole authorship of the original design or a verified backend implementation.

Approach

How I worked through the problem.

01

Organize the content across five pages

The current frontend contains Universe, Fighters, Clashes GP, Labs & Media, and Shop. Static HTML pages share visual assets and navigation without requiring a frontend build step.

02

Reuse styling and interaction logic

A shared css/style.css file supplies responsive presentation, while js/main.js handles interface behavior. The visible code includes mobile navigation, scroll reveals, animated tickers and other page interactions.

03

Support bilingual navigation

An English/Spanish toggle uses browser storage to retain the visitor’s language selection. The interface connects content translation with the same shared navigation and presentation system.

04

Document development boundaries

Keep the current static frontend distinct from any more developed local version or backend prototype. Specific modifications and additional services should be documented once their code is available for review.

Result & scope

What the work delivered.

The public fork provides a five-page static frontend with bilingual interaction and a consistent visual identity. It serves as the documented starting point for further frontend work; more specific contribution claims depend on the updated development version being published and reviewed.

Scope & next steps

  • The repository is a fork of daveeedlr/raaz-borg. The case study does not attribute all original design or functionality to me.
  • The scope of my changes will be updated when the more developed local version is pushed and its differences can be reviewed.
  • The currently documented public fork is static HTML/CSS/JavaScript. A Node.js or PostgreSQL backend is not established by the available code.
  • The GitHub Pages address depends on the fork’s publishing configuration; the repository is the evidence for current source features.

Learning & progression

How this work develops my practice.

Work on an existing design system is easiest to assess when inherited features and new modifications are clearly separated. That provenance makes both technical review and a portfolio account more useful.
